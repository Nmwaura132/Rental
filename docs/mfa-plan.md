# MFA Plan for Landlord + Caretaker Accounts

**Status**: Design only — not implemented. Created 2026-05-16 from `/cso` Finding 9.
**Owner**: Peter Mwaura
**Targets first implementation**: Post-launch, after first paying landlord onboards.

## Why MFA matters here

Kasa's landlord role has financial authority. A landlord account can:
- See every tenant's national ID number, phone, KRA PIN
- Trigger M-Pesa STK pushes that charge tenants
- Cancel leases (which marks units vacant and orphans payment history)
- Export the entire rent roll as PDF

Right now we have **single-factor auth**: phone number + password. The password
reset path is **SMS OTP** — and SMS is vulnerable to SIM-swap, which is a
documented attack in Kenya (cf. Safaricom case law on SIM-swap fraud). So a
phone-based reset is **not** a true second factor; it shares the attack vector
with the primary credential.

Tenants don't need MFA — their account exposure is themselves.

## Threat model (the specific attack we're closing)

1. Attacker obtains a landlord's email/phone from public records.
2. Attacker calls Safaricom posing as the landlord, requests SIM swap with
   forged ID.
3. Attacker receives password-reset OTP on the new SIM, resets the password.
4. Attacker logs in as landlord, exports tenant ID + KRA PIN dataset.
5. Optionally: triggers fake STK pushes via the `Pay on behalf of tenant`
   endpoint to siphon rent into an attacker-controlled paybill.

MFA closes step 4 because login itself requires a TOTP code generated by an
app the attacker doesn't control.

## Recommended approach: TOTP via `django-otp` + `django-two-factor-auth`

**Why TOTP over SMS-as-second-factor:**
- TOTP secrets live in an authenticator app (Google Authenticator, Authy,
  1Password, Aegis) — separate from the phone number.
- A SIM swap doesn't give the attacker the TOTP secret.
- No incremental SMS cost per login.
- Works offline once enrolled.

**Why `django-two-factor-auth` over rolling our own:**
- Battle-tested. Used by major Django apps for years.
- Handles enrollment QR code, backup tokens, recovery codes.
- Integrates with Django admin and DRF cleanly.

**Why not WebAuthn/passkeys:**
- Kenyan mid-market landlords mostly use Android phones without security keys.
- Adds an Android-passkey infra dependency (Google Play Services).
- Re-revisit when passkey adoption among Kenyan business users hits ~50%.

## Implementation sketch

### Backend (Django)

1. Add deps to `backend/requirements.txt`:
   ```
   django-otp==1.5.0          # core OTP framework
   django-two-factor-auth==1.17.0  # views + flows on top of django-otp
   qrcode==7.4.2              # enrollment QR code rendering
   ```

2. Add to `INSTALLED_APPS` in `config/settings.py`:
   ```python
   "django_otp",
   "django_otp.plugins.otp_totp",
   "django_otp.plugins.otp_static",   # backup codes
   "two_factor",
   ```

3. Add `django_otp.middleware.OTPMiddleware` to `MIDDLEWARE`
   (after `AuthenticationMiddleware`).

4. Extend the JWT login flow:
   - Create `MFAVerifyView` that accepts `{access_token, totp_code}` and
     returns a fresh `access_token` only after the TOTP matches.
   - The initial `/api/v1/auth/login/` call should detect whether the user
     has MFA enrolled (`user.totpdevice_set.filter(confirmed=True).exists()`)
     and either return the full token pair (no MFA) or a short-lived
     `mfa_pending_token` that the client trades for a full token via
     `MFAVerifyView`.

5. Enforce MFA for landlords + caretakers via a custom DRF permission:
   ```python
   class RequiresMFAIfLandlord(BasePermission):
       def has_permission(self, request, view):
           if request.user.role in (Role.LANDLORD, Role.CARETAKER):
               return request.user.is_verified_for_mfa  # property on User
           return True
   ```

6. Migration plan:
   - **Phase 1** (week 0): ship enrollment endpoints. Landlords can opt in.
   - **Phase 2** (week 2): admin dashboard shows MFA-status per landlord.
     Email + SMS nudges to non-enrolled landlords.
   - **Phase 3** (week 4 or first incident, whichever first): MFA becomes
     required for any landlord managing > 5 units. Existing accounts have
     30 days to enroll before the lock-out kicks in.

### Mobile (Flutter)

1. Add a TOTP enrollment screen in `mobile/lib/features/auth/`:
   - Calls `POST /api/v1/auth/mfa/enroll/` -> receives QR code SVG + recovery
     codes.
   - Renders QR with `flutter_svg` or `qr_flutter`.
   - Confirms enrollment by submitting a TOTP code.

2. On login, if backend returns `mfa_required: true`, route to an MFA prompt
   screen. Otherwise proceed to dashboard.

3. Store recovery codes via `flutter_secure_storage` — encourage user to
   screenshot or write down too.

### Tests

Add to `backend/tests/test_mfa.py`:
- Login with correct password but no TOTP -> returns `mfa_required: true`
- Login with valid TOTP -> returns access + refresh
- Login with stale TOTP (>30s old) -> 401
- Landlord without enrolled MFA + RequiresMFAIfLandlord -> 403

## Open decisions

1. **Caretakers**: required from day one, or only when they manage > N units?
   *Recommendation: required only for caretakers of properties with > 10 units.*

2. **Recovery flow if both phone + authenticator are lost**: admin-mediated
   identity proof + new enrollment, or self-serve via recovery codes only?
   *Recommendation: recovery codes only (self-serve). Admin-mediated is a new
   social engineering surface.*

3. **Trust this device for 30 days**: convenience vs. security tradeoff.
   *Recommendation: yes, but tied to refresh-token rotation — when refresh
   expires (30 days), MFA is re-prompted.*

4. **Should tenants ever get MFA?** Only if they're paying for it as a feature.
   Not for v1.
